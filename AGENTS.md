# Repository Guide

## Purpose and entry points

This flake manages one user's development environment on two targets:

- Linux: standalone Home Manager configuration `homeConfigurations.linux`
  (`x86_64-linux`).
- macOS: nix-darwin configuration `darwinConfigurations.macbook-pro`
  (`aarch64-darwin`), with Home Manager for user `yueting`, nix-homebrew, and
  declarative Homebrew packages/casks.

Start with `flake.nix` to understand target composition. `darwin-configuration.nix`
contains system-level macOS settings. Files under `modules/` are Home Manager
modules except `font-packages.nix`, which is a package-list helper imported by the
Darwin system configuration.

## Configuration layout

`modules/common.nix` is the shared Home Manager entry point. It imports:

- `shell.nix`: Fish, shell environment/PATH, Starship, Zoxide, Direnv, and the
  generated Fish baseline.
- `tools.nix`: shared CLI packages and Syncthing.
- `ui.nix` and `font-packages.nix`: UI and font setup.
- `editor.nix` and `emacs.nix`: Neovim and Doom Emacs dependencies/settings.
- `terminal.nix`: generated Kitty and Ghostty base configs plus editable local
  overrides.
- `dotfiles.nix`: editable out-of-store links for application configurations.

Platform modules add only platform-specific behavior: `modules/linux.nix` sets the
Linux home directory and SSH keychain setup; `modules/darwin.nix` sets the macOS
home directory and a launchd GUI `PATH`. Keep shared behavior in `common.nix` or
one of its focused imports, and keep system-wide macOS settings in
`darwin-configuration.nix`.

Application-owned configuration is under `dotfiles/config/`:

- `nvim/` is the LazyVim configuration; use `nvim/stylua.toml` for Lua formatting.
- `doom/` is the Doom user configuration.
- `kitty/local.conf` and `ghostty/local.conf` are editable overrides. Their base
  configs are generated by `modules/terminal.nix`; do not edit generated files in
  `~/.config`.
- `fish/local.fish` is the editable Fish override. Home Manager generates
  `fish/config.fish` with the cross-platform baseline, then sources this linked
  file; do not edit the generated `~/.config/fish/config.fish`.
- `aerospace/aerospace.toml` is checked in, but is not currently linked or
  installed by a Nix module. Treat deployment of it as a separate change unless
  you also add the required wiring.

`modules/dotfiles.nix` links the Neovim and Doom directories with
`mkOutOfStoreSymlink`. Its default `dotfiles.repoPath` is
`$HOME/src/dotfiles-nix`; override that option when activating from another
location, otherwise the live links will point at the wrong repository.

Byobu's managed `~/.byobu/backend` is shell-sourced by its launcher, so it must
be an assignment (`BYOBU_BACKEND=tmux`), not the bare word `tmux`.

## Working conventions

Use two-space indentation in Nix and Lua. Follow nearby style in Emacs Lisp:
feature-focused sections, `setq` for configuration, and `my/` prefixes for
personal functions. Keep package declarations in Nix modules and detailed app
settings in `dotfiles/config/`. Preserve `home.stateVersion` and
`system.stateVersion` unless intentionally performing a state-version migration.

Before editing, run `git status --short` and preserve unrelated working-tree
changes, especially application-managed lock files such as LazyVim's
`lazy-lock.json`. Do not commit credentials; keep secrets in the established
`auth-source` pattern.

## Commands and validation

- `make check` runs `nix flake check --all-systems`; use it as the first check for
  Nix changes.
- `make build` builds without activating, selecting the current OS. Use
  `make build-linux LINUX_HOST=linux` or `make build-mac MAC_HOST=macbook-pro`
  when an explicit target is needed.
- `make apply` selects the current OS and mutates the active environment.
  `make apply-linux` uses the Home Manager app exported from the locked flake;
  `make apply-mac` similarly uses the locked nix-darwin app with `sudo`.
- `make init` bootstraps the platform-specific manager; `make doctor` reports
  local Nix/Home Manager diagnostics.
- `make update` runs `nix flake update`, checks and builds the result, applies it,
  then upgrades only the formulae and casks declared in nix-darwin's generated
  Brewfile on macOS. Review every `flake.lock` change before committing.

Homebrew itself is installed by `nix-homebrew`, and its client source is pinned
through `flake.lock`; formula and cask versions are intentionally not pinned.
Keep `homebrew.onActivation.autoUpdate` and `upgrade` disabled so regular
activation remains idempotent. `make update` explicitly refreshes Homebrew
metadata and upgrades only the formulae and casks declared in nix-darwin's
newly evaluated generated Brewfile.

For Nix changes, run `make check` and the relevant non-mutating build command.
For application configuration, also start the affected application after an
activation and test the changed startup path. `make apply` alone is not adequate
validation because it changes the user's environment.

## Change and review expectations

Keep commits focused with short imperative subjects. Pull requests should state
the behavior changed, validation performed, and any `flake.lock` update. Include
screenshots only for visible UI changes.
